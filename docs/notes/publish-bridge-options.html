Time2Crack — suite de la note de synthèse

Quatre façons de faire tenir le pont entre main et la production

Aucun mécanisme n'existe aujourd'hui : la publication sur time2crack.eu se fait à la main, sans trace, vers la branche codex-site-publish que GitHub Pages sert directement.

Contrainte commune aux quatre options : main n'est pas publiable tel quel. Son index.html racine a un canonical erroné (time2crack.com), il lui manque les hreflang absolus et le favicon corrigé, et il référence encore des assets ML/ONNX absents. Toute solution doit préserver cette passe de correctifs, pas la contourner.

1

Pages pointe directement sur main

Effort moyen · discipline élevée

On change la config GitHub Pages (source.branch: "main") et les correctifs de publication (canonical, hreflang, favicon, retrait ONNX) deviennent un script exécuté en pre-commit ou juste avant chaque commit sur les fichiers concernés.

Caractéristiques

  • Une seule branche à connaître et à maintenir
  • Publication à chaque push sur main
  • Correctifs appliqués en amont, avant le commit

Avantages

  • Zéro synchronisation manuelle entre deux branches
  • main devient la seule source de vérité, sans ambiguïté
  • Mise en place la plus simple conceptuellement

Inconvénients

  • Tout commit expérimental part directement en prod
  • Le WIP en cours (v2/public/) doit rester toujours propre
  • Aucun filet de sécurité avant déploiement

Convient si l'équipe est prête à traiter chaque commit sur main comme potentiellement public, ou à passer systématiquement par des PR revues avant merge.

2

Branche release scriptée

Effort moyen · discipline modérée

On garde une branche de publication séparée, mais on remplace le portage manuel par scripts/sync-release.sh : merge de main, application des correctifs, push. GitHub Pages reste branché sur cette branche (renommage propre de codex-site-publish).

Caractéristiques

  • Deux branches : main (dev) et release (publiée)
  • Un script unique fait tout le travail de portage
  • Déclenchement toujours manuel, mais outillé

Avantages

  • Séparation dev/publication conservée — utile si main contient du WIP cassé
  • Un seul point d'entrée, traçable et réexécutable
  • Élimine la dérive silencieuse actuelle

Inconvénients

  • Reste un geste humain à déclencher à chaque publication
  • Le script de correctifs doit être écrit et testé une première fois
  • Oubli toujours possible si personne ne lance le script

Convient si on veut garder la main sur le moment de publication sans réinvestir dans un pipeline CI complet.

3

GitHub Actions automatique

Effort élevé · discipline faible

Un workflow .github/workflows/deploy.yml qui, à chaque push sur main (ou sur un tag), checkout, applique les correctifs via un petit script, et publie le résultat — soit sur codex-site-publish, soit directement en artifact Pages via actions/deploy-pages.

Caractéristiques

  • Pipeline CI natif GitHub, déclenché par push ou tag
  • Correctifs de publication exécutés côté serveur, pas en local
  • Peut être combiné à une protection de branche

Avantages

  • Zéro geste humain après la mise en place initiale
  • Impossible d'oublier de publier
  • Review possible via PR avant que le merge ne déclenche la publication

Inconvénients

  • Coût de mise en place le plus élevé des quatre
  • Demande de définir ce qui est « publiable » (tag vs. chaque commit)
  • Débogage d'un pipeline cassé plus indirect qu'un script local

Convient si les publications deviennent fréquentes et qu'on veut retirer complètement l'étape manuelle de l'équation.

4

Script publish.sh sur le worktree existant

Effort faible · discipline modérée

On garde CrackDate-publish tel quel — déjà en place comme worktree — et on ajoute bin/publish.sh qui automatise ce qui se ferait à la main : fetch, merge de main, correctifs, puis push vers codex-site-publish.

Caractéristiques

  • Réutilise l'infrastructure déjà présente (worktree existant)
  • Aucune nouvelle branche, aucun CI à configurer
  • Un seul script local à lancer avant chaque publication

Avantages

  • Changement le plus léger des quatre
  • Corrige immédiatement le flou actuel, sans nouveau composant
  • Bon compromis si les publications restent peu fréquentes

Inconvénients

  • Reste manuel — il faut se souvenir de lancer le script
  • Ne passe pas à l'échelle si le rythme de publication s'accélère
  • Aucune trace CI si le script échoue silencieusement

Convient si l'objectif est de corriger le flou tout de suite, à coût quasi nul, quitte à migrer plus tard vers une option plus automatisée.

Recommandation

Démarrer par l'option 4 : elle corrige immédiatement le flou actuel sans nouveau composant à maintenir, en réutilisant le worktree déjà en place.

Basculer vers l'option 3 si les publications deviennent fréquentes — l'option 2 reste un palier raisonnable entre les deux si on préfère garder la main sur le déclenchement sans investir dans un pipeline CI complet.
